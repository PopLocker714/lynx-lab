# Стандарт пакетов Lynx Lab · v1

## Цель и границы

Закрывать базовые потребности production-приложений Lynx небольшими надёжными
пакетами, понятными разработчикам и агентам. Основная платформа — Lynx;
Sparkling — первый проверяемый host. Поддержка другого host требует собственных
проверок. Требования Lynx и особенности host описываются отдельно.

Пакеты остаются самостоятельными репозиториями. Этот документ — общий стандарт,
[standards/](../standards/README.md) — эталонные конфиги для последовательного
внедрения. Их наличие здесь **не означает**, что четыре пакета уже мигрированы.
Порядок пилота: crypto → secure-store → app-lifecycle → edge-to-edge.

## От задачи до выпуска

1. Описать пользовательский сценарий, границы пакета и критерии приёмки.
2. Исследовать 2–3 подходящих аналога: RN/Expo, Tauri, при необходимости
   Flutter/Capacitor и существующие Lynx-пакеты. Читать реализацию, тесты,
   исправления и ограничения; сверять native API с Android/Apple.
3. Зафиксировать контракт: входы/выходы, ошибки, события, начальное состояние,
   единицы, очередность, потоки, ownership, cleanup, платформенные различия.
4. Если ключевой вопрос не подтверждён — небольшой воспроизводимый spike.
5. Реализовать минимальное решение и проверки существенных рисков. Сохранять
   опубликованные контракты при рефакторинге; изменения поведения отдельно.
6. Выполнить автоматические проверки и независимое read-only review изменений
   API, native lifecycle, async/error handling и других нетривиальных изменений.
7. Установить упакованный tarball в consumer host, проверить autolink, Debug и
   Release; на Android — R8. Проверить сценарии на обеих заявленных платформах.
8. Сопоставить доказательства, документацию, changelog и релизный артефакт.
   Публикация — отдельное разрешённое действие.

Исследование заканчивается решением «берём / отвергаем / проверяем» с причинами.
Для переноса кода сохранить upstream commit/tag, лицензию/notice, существенные
изменения и способ отслеживать upstream fixes. Чужой bridge не переносит гарантии
его runtime в Lynx. Криптографические примитивы предоставляет платформа или
проверенная зависимость; собственные алгоритмы не входят в обычную разработку.
Workaround имеет воспроизведение, источник, ограничение по версиям и условие удаления.

## Читаемость и TypeScript

- Четыре пробела, без табов; целевая длина строки 100. Formatter определяет
  переносы; не уплотнять код ради лимита строк. TS/JS: одинарные кавычки,
  semicolons as needed, trailing commas ES5 — сохраняем существующие соглашения.
- YAML — 2 пробела, Makefile recipes — табы по синтаксису. Generated/vendor код
  не переформатировать; JSON и собственный TS/Kotlin/ObjC используют 4 пробела.
- Понятные имена, единицы в контракте, небольшие связные ответственности,
  явные эффекты. Пустые строки отделяют смысловые шаги.
- Комментарии объясняют invariant, причину и ограничение, public API — контракт.
  Нет квот строк/классов, обязательного DI, FSD или интерфейса на каждую функцию.
- TS public API → bridge → платформенная реализация; React-обёртки отдельно,
  когда нужны. Внутренний native-код идиоматичен своей платформе. ObjC не требует
  переписывания на Swift. Общую абстракцию оправдывает общий контракт.
- База TS: strict, noUncheckedIndexedAccess, exactOptionalPropertyTypes,
  noImplicitOverride, noImplicitReturns, noFallthroughCasesInSwitch,
  noUnusedLocals/noUnusedParameters, verbatimModuleSyntax.
- Вход bridge — unknown с runtime-проверкой. Типы не заменяют валидацию.
  Не маскировать ошибки через any, двойные assertions или необъяснённый `!`.
  Локальный interop допускается с проверкой и объяснением. Не добавлять schema
  framework ради нескольких проверок.
- Строгость не должна ломать прежний API: если optional-поле допускало явный
  undefined, сохранить это в типе. `@ts-ignore` и глобальное ослабление flags
  не являются способом завершить миграцию.
- skipLibCheck по умолчанию false. Временный true допустим лишь для доказанного
  дефекта dependency declarations с записью исключения; это не полная проверка
  зависимых типов. TS/Biome фиксируются точными версиями и lockfile.
- Runtime, тесты и инструменты имеют явные TS-окружения. Не добавлять DOM/Node
  globals в runtime ради удобства тестов; проверять публичные declarations отдельно.

## Native и bridge

Для каждого entrypoint известны поток вызова, очередь работы и доставки результата.
Promise не гарантирует фоновое выполнение. UI выполняется на требуемом ОС потоке;
блокирующие операции не занимают UI thread. Синхронный API отдельно обосновывается.

У listener, observer, callback, очереди и ссылки на Activity/ViewController есть
владелец и момент освобождения. Проверяются уничтожение и повторное создание
LynxView, несколько views, поздний callback, гонки и unsubscribe. Одноразовый
запрос завершается не более одного раза; поведение при teardown описано явно.

Ошибки имеют стабильный контракт. Отсутствующее значение, unsupported,
unavailable, permission denied и внутренняя ошибка различимы. Не превращать
сбой в успех, не отдавать secrets/PII через logs/errors. Уже существующий
документированный no-op сохраняется до отдельного решения об изменении API.

Контрактные тесты покрывают реальную границу JS/native: сериализацию, Unicode/NUL,
числа, размеры и отсутствие значений по применимости. Mock не доказывает работу
bridge. Storage: failed overwrite, corruption, lock/key loss, persistence и
backup/reinstall; UI: первый кадр, rotation, keyboard и background; lifecycle:
начальное состояние, порядок событий, cleanup и повторная подписка.

## Проверки, warnings и stable

Общие имена команд определены в [standards/README.md](../standards/README.md).
Быстрые TS checks выполняются на каждом PR; native checks — при изменении native,
его конфигурации/зависимостей или bridge-контракта. Перед выпуском применяется
полная релевантная матрица. Docs-only правка не требует аппаратного прогона.

Native минимум: Kotlin compile + Android Lint + formatter; ObjC compile diagnostics
+ clang-format + Clang static analysis. Sanitizers и stress tests — по риску
ownership/concurrency, с указанием доступной платформы запуска. Не подменять
consumer native build одним podspec lint. В CI закреплять версии toolchains.

Собственный код: ноль ошибок и необработанных warnings в согласованных checks.
Biome запускается с `--error-on-warnings`. Не включать глобальный Werror для
всех сторонних SDK. Подавление точечное, с причиной; записи исключений содержат
точную диагностику/область, источник, ответственного и дату пересмотра. Истёкшее
исключение пересматривается до merge. blanket ignores и `|| true` не делают check
успешным. Проверка, которую не запускали, имеет статус not-run.

Для security audit проверять фактически поставленные зависимости, включая bundled
dependencies, а не только lockfile. Временное исключение содержит advisory ID,
оценку достижимости, владельца, срок и проверяемую привязку к графу зависимостей.
Истечение срока или изменение графа блокирует gate до пересмотра исключения.

Stable требует:

- Чёткой области support и проверенной установки из пакета в заявленные host.
- Debug/Release smoke на Android и iOS, включая реальные устройства для
  сценариев, зависящих от ОС/железа; Release Android с R8.
- Закрытых критических сценариев, без известных блокеров безопасности/потери
  данных/основного сценария; documented limitation не легализует такой блокер.
- Независимого review существенных изменений и актуальных EN/RU docs.
- Связи results → package commit/version → tarball hash → host lock/toolchain
  → runtime/OS/device → сценарий/результат. Проверяется именно поставляемый код.

Совпадение `node_modules` с tarball не доказывает native integration. Consumer gate
также проверяет фактически подключённые Gradle source sets/projectDir, CocoaPods
sources и используемую регистрацию модулей; старые autolink/Pods могут продолжать
ссылаться на другой каталог. Сохранять resolved paths и hashes исходников в evidence;
отрицательные fixtures должны отклонять stale sources и отсутствующую регистрацию.
Границы поддерживаемого host adapter описывать явно.

Новая правка не обнуляет старые доказательства, но они не подтверждают изменённый
код автоматически. Определить, что затронуто, и повторить эти проверки. Выпускать
артефакт, прошедший release gate; если после проверки меняется содержимое, повторить
затронутые проверки и сохранить новый hash. CI release должен зависеть от нужных
checks для того же commit, а не только от успешного build. Выпуск остаётся ручным.
Если release tooling меняет version/changelog перед упаковкой, QA выполняется
после этих изменений над финальным архивом. Receipt и consumer evidence сохраняют
его hash; публикация не должна незаметно создавать другой архив.
Реализация D14 использует два ручных этапа одного release.yml: prepare сохраняет
архив, publish проверяет исходный workflow run и committed QA receipt, повторяет
audit и передаёт тот же tarball publisher. Receipt не доказывает истинность теста:
ответственный проверяет содержание evidence, а gate — структуру, hash и полноту.

## Документация для людей и агентов

README: языки EN/RU → название/бейджи → назначение → platform/feature support →
требования Lynx/host → установка и обязательные настройки → рабочий пример →
краткий API/важные ошибки → ссылки/contribution/license. Бейджи отражают реальное
состояние. Существенные ограничения остаются рядом с возможностью в README.

В reference — точный API, в how-to — интеграция/диагностика, в implementation —
причины устройства. Не создавать пустые документы ради шаблона. Публичные типы
документируются TSDoc; примеры проверяются компилятором и, по риску, consumer host.
API signatures проверяются diff деклараций или API report; он не обнаруживает
изменение runtime-семантики, поэтому нужны контрактные тесты и review.

Каждый потребительский документ в пакете имеет EN-оригинал и полную RU-пару;
изменяются вместе. В tarball доступны документы, на которые ссылается README,
либо используются устойчивые публичные ссылки на соответствующую версию.
AGENTS содержит команды и указатели на канонические правила, не второй API.
Лабораторный стандарт и внутренняя история могут оставаться на русском.

Support и tested matrix — разные сведения. Порядок обновлений и версий задан в
[compatibility-policy.md](compatibility-policy.md).

риск или уменьшать стоимость поддержки; само количество проверок не цель.
