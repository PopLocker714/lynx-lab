# Совместимость и обновления host

## Что обещаем

Версия пакета, native Lynx runtime, compile-time SDK, ReactLynx, host, ОС и build
toolchain — разные оси. Версию runtime определяем по реальным зависимостям host,
не по compileOnly пакета. Чужой major/minor/patch не доказывает совместимость.

Единица проверки — именованный профиль с точными версиями и lockfile. Матрица
содержит package version/commit и tarball hash, host/version, native Lynx Android/iOS,
ReactLynx, compile SDK/target/min SDK, iOS deployment target, JDK/Kotlin/Gradle/AGP,
Xcode/CocoaPods, ОС/устройство, Debug/Release, дату, сценарии и ссылку на evidence.
Не заполнять поля предполагаемыми результатами.

Для каждого поддерживаемого host целевой набор — текущий рекомендуемый профиль
и предыдущий поддерживаемый профиль. Это две проверенные связки, а не обещание
совместимости со всеми версиями между ними или вечной поддержки любой старой ОС.
При первом внедрении может быть один профиль: отсутствие второго указывается явно.

Статусы: verified, candidate (проверяется), blocked (известная проблема),
unverified (нет результата), retired (поддержка прекращена). Рекомендованный
профиль выбирается только среди verified. Результаты симулятора, устройства и
compile-only не взаимозаменяемы. Проверка на новой ОС не доказывает minimum OS.

Заявленные диапазоны support и peerDependencies согласованы с API/ABI анализом
и проверками граничных профилей; точные tested-комбинации перечислены отдельно.
Не расширять диапазон автоматически до latest или будущих major. Для непроверенного
minimum явно показывать границу проверки и закрыть её перед обещанием stable support.
Runtime feature detection полезен для реальных возможностей, но не заменяет матрицу.

## Когда host обновился

1. **Обнаружить и оценить.** При новой версии host/Lynx/toolchain прочитать release
   notes и затронутые upstream changes: autolink, bridge, threading/lifecycle,
   упаковка, API/ABI и минимум ОС. Зафиксировать кандидата. Автоматический мониторинг
   пока не настроен: проверять перед началом работы над пакетом и перед выпуском.
2. **Сохранить baseline.** Не менять рекомендуемый профиль. Создать отдельный
   worktree/consumer fixture с точным новым host и lockfile; сохранить старый.
   Проверить диск до зависимостей/сборок. Обновлять одну ось за раз, когда возможно;
   вынужденный набор обновлений описать явно.
3. **Проверить текущий артефакт.** Установить уже выпущенный tarball, а не source
   symlink. Запустить static/type/contract checks, autolink, Debug/Release с R8,
   основной сценарий и затронутые native/lifecycle/security сценарии на обеих ОС.
   Для неопубликованного пакета использовать tarball конкретного commit.
4. **Локализовать отказ.** Сравнить старую и новую связку; по возможности минимальный
   repro. Различить дефект пакета, host, toolchain и снятый платформенный API.
   Сборка с отключённой проверкой или фиктивным успехом не подтверждает поддержку.
5. **Исправить или ограничить.** Исправление в пакете сопровождается regression
   test и review. Workaround узкий, с версией/причиной/условием удаления. При
   upstream-блокере оставить candidate blocked и дать работающую связку; публикация
   upstream issue/сообщения требует соответствующего разрешения пользователя.
6. **Проверить назад.** Новый пакет проверить и на новой, и на прежней поддерживаемой
   связке. Нельзя чинить новый host незаметной потерей поддержки прежнего.
7. **Обновить матрицу.** После успеха отметить verified, выбрать recommended,
   обновить EN/RU docs и нужные dependency ranges. Если код/metadata пакета не
   изменились, достаточно обновить evidence/docs: новый npm release не обязателен.
8. **Выпустить при необходимости.** Выбрать SemVer, пройти stable gate для нового
   артефакта и выпустить только по разрешению. При регрессии рекомендовать прежний
   проверенный пакет+host, не перезаписывать опубликованный tarball.

Проверять host update до перехода собственных production-приложений на него.
Не обещать срок адаптации без оценки изменения. Критичные security fixes имеют
приоритет; если старый host небезопасен, документировать риск и путь обновления,
а не продолжать рекомендовать его ради формального сохранения двух профилей.

## Версии пакетов и прекращение поддержки

У каждого пакета свой SemVer; общий релиз всех четырёх не обязателен.

- **Patch:** совместимое исправление, включая исправление работы с новым host,
  если прежние гарантии сохранены.
- **Minor:** обратно совместимые новые возможности. Добавленная поддержка нового
  host с новым adapter/API без удаления старого поведения может войти сюда.
- **Major:** несовместимое изменение API/ошибок/семантики/данных или прекращение
  заявленной поддержки host/runtime/minimum OS. Для снятия support заранее
  публиковать deprecation и migration path, кроме экстренного security решения.
- **0.x:** breaking change явно отмечается и повышает minor; patch не используется
  для скрытого нарушения уже описанного контракта. Prerelease не помечается stable.

Это локальная политика совместимости поверх [SemVer](https://semver.org/).
Повышение минимума host не прячется в косметический refactor или dependency patch.
Сохранять последнюю рабочую версию для retired-профиля; активный backport/security
support старой ветки объявляется отдельно и не подразумевается автоматически.

Историческое evidence сохраняется. Новая версия host не делает прежний результат
ложным, но требует нового результата для новой связки. Просроченная дата пересмотра
означает необходимость проверки актуальности, а не выдуманный новый pass.
