# Как работать в этом репозитории

Это база знаний, а не код. Её ценность в том, что ей можно доверять через три месяца.
Поэтому правила ниже про доказуемость, а не про стиль.

## Первое действие в новой сессии

Прочитать **[STATE.md](STATE.md)**, затем **[docs/01-platform-traps.md](docs/01-platform-traps.md)**.
Первый возвращает в контекст, второй не даёт наступить на то, на что уже наступали.
Тридцать семь ловушек, и почти каждая выглядит как рабочий код.

**STATE.md обновляется в конце каждого захода**, иначе он бесполезен. Что в нём
двигать: таблицу пакетов, доказанное на железе, незакрытые хвосты, следующий шаг.

## Главное правило

**Ни одного утверждения без источника, проверенного в эту сессию.** Не по памяти,
не по блог-посту, не по тому, что «так было в прошлый раз». Первичные источники в порядке
убывания веса:

1. Исходники `lynx-family/lynx` и `tiktok/sparkling` на конкретном теге
2. Опубликованные npm-тарболы (`npm pack` и читать, а не читать README)
3. Официальные доки на `lynxjs.org`
4. Issue и PR с датами
5. Всё остальное помечать как `verified-secondary`

Если проверить не удалось, писать «не удалось подтвердить» и объяснять почему.
Пустое место честнее догадки.

## Шапка каждого документа

```yaml
---
verified: 2026-08-21        # когда факты последний раз подтверждались
lynx_version: 4.0.1         # против какой версии
sparkling_version: 2.1.0-rc.36
status: draft | spec | building | shipped
---
```

Факт старше трёх месяцев считается неподтверждённым. При обновлении двигать `verified`
и дописывать строку в `CHANGELOG.md`.

## Жизненный цикл дефекта

У каждого пакета есть реестр дефектов с ID (`P1`, `N4`, `T3`). Формат строки:

| Поле | Значение |
|---|---|
| ID | `P1`, стабилен навсегда, не переиспользуется |
| Severity | `Блокер` / `Важно` / `Мелочь` |
| Статус | `открыт` / `починен` / `не подтвердился` / `не чиним` |
| Что ломается | конкретный сценарий отказа, не абстракция |
| Как чинить | конкретное действие |
| Источник | URL или путь в исходниках |

**Дефект никогда не удаляется.** Меняется только статус. Если оказалось, что дефекта нет,
ставим `не подтвердился` и пишем, чем опровергнут. Это важнее, чем кажется: половина
времени уходит на то, чтобы не проверять одно и то же дважды.

Когда реализация вскрывает новый дефект, он получает следующий свободный ID в своём
пространстве и запись о том, на каком шаге всплыл.

## Когда спека расходится с реальностью

Реальность выигрывает всегда. Порядок действий:

1. Правим спеку пакета
2. Дописываем строку в `DECISIONS.md` с датой и причиной
3. Если находка общая для всех пакетов, она поднимается в `docs/01-platform-traps.md`
   и получает ID в пространстве `T`

Последнее особенно важно. Общая ловушка, оставленная в спеке одного пакета, будет
заново найдена при работе над следующим.

## Оценки сроков

В спеках стоят оценки для одного человека с реальным тестированием на устройствах.
Работа в паре с ассистентом идёт быстрее, но узкие места остаются те же и они физические:

- прогон на реальных устройствах трёх версий ОС
- поведение при убитом процессе
- лаунчеры OEM (MIUI, HyperOS, ColorOS)
- ревью в сторах

Ускорять оценку без прогона по устройствам нельзя. Можно сокращать объём работы,
и это надо писать явно.

## Документация пакетов: два языка

Каждый пакет несёт **два README**, и это правило, а не пожелание.

| Файл | Язык | Роль |
|---|---|---|
| `README.md` | английский | основной. Именно его показывает страница пакета на npm, и аудитория экосистемы Lynx международная |
| `README.ru.md` | русский | полная версия, не сокращённая выжимка |
| `CONTRIBUTING.md` | английский | основной |
| `CONTRIBUTING.ru.md` | русский | полная версия |

Правило распространяется на **любой** документ, попадающий в репозиторий пакета:
английский оригинал плюс русская пара с суффиксом `.ru`.

Первой строкой обоих идёт переключатель:

```md
> **English** · [Русский](./README.ru.md)
```
```md
> [English](./README.md) · **Русский**
```

Обе версии обязаны уезжать в npm-тарбол (`files` в `package.json`) и обе проверяются
в `scripts/check-publishable.mjs`. Расхождение версий это баг: правка одной без другой
не считается законченной работой.

## Инструменты и версии

**Bun 1.4.0 это базовая версия** (вышла 2026-08-20). Локально, в `packageManager`
и в CI должна стоять одна и та же.

**`bun-version: latest` в CI запрещён.** Ставить точную версию. Иначе сборки уезжают
сами: 20 августа `latest` перешёл на 1.4, и релиз пакета прошёл на версии, отличной
от той, на которой шла разработка, без единого коммита.

Обязательные проверки цепочки поставок в CI каждого пакета, все три появились в 1.4:

| Команда | Что ловит |
|---|---|
| `bun audit` | Уязвимости в дереве зависимостей. Падает на находке |
| `bun dedupe --check` | Две версии одного пакета в `bun.lock`. Такой баг воспроизводится только у потребителя |
| `bun pm licenses` | Лицензии зависимостей. Не падает, пишет в лог для аудита |

**Шардинг тестов (`--shard`, `--parallel`) добавлять только когда набор реально
большой.** У пакета на два метода 19 тестов идут 200 мс, и разбиение по раннерам
там чистый карго-культ.

## Раскладка на диске

Репозиторий знаний остаётся репозиторием знаний, но всё, что относится к Lynx,
лежит рядом, чтобы сессия, начатая в любом пакете, наследовала этот `CLAUDE.md`
и правила выше (Claude Code читает `CLAUDE.md` из всех родительских папок).

| Папка | Что там | В git этого репозитория |
|---|---|---|
| `docs/packages/<name>.md` | спека пакета | да |
| `packages/<name>/` | **свой** git-репозиторий пакета (`PopLocker714/lynx-<name>`) | нет, в `.gitignore` |
| `apps/<name>/` | пробники на `create-sparkling-app`, одноразовые | нет, в `.gitignore` |
| `upstream/lynx`, `upstream/sparkling` | shallow-клоны апстрима на тегах, для проверки фактов по исходникам | нет, в `.gitignore` |

Спека и код пакета сходятся по имени: `docs/packages/lynx-edge-to-edge.md` ↔
`packages/lynx-edge-to-edge/`. Новый пакет клонируется или создаётся в `packages/`,
а не в `~/Documents/dev`. Решение и его условия пересмотра: `DECISIONS.md`, D7.

Тег в `upstream/lynx` должен совпадать с `lynx_version` в шапке документа,
против которого идёт проверка: `git -C upstream/lynx grep -n <шаблон> 4.0.1 -- core`.

## Что сюда не кладём

- Секреты, токены, ключи, пути с именем пользователя
- Код самих пакетов в **этот** git. Он живёт в своих репозиториях и лежит рядом
  в `packages/` только как вложенный клон, см. «Раскладка на диске»
- Пересказ официальной документации. Только то, что документация не говорит
  или говорит неверно
